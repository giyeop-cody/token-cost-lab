# 실험 A 프로토콜 — 재작업 대결 (미실시, 설계만)

> 상태: **설계 완료, 실행 대기.** 이 문서는 사전등록(pre-registration)이다.
> 실행 전에 설계를 공개해, 결과가 나온 뒤 기준을 바꾸는 것(HARKing)을 방지한다.

## 0. 왜 이 실험이 최우선인가

케이스 스터디(이 폴더)는 **1턴 생성**의 비교다. 결과는 −7~−8.3% 절감으로,
`sensitivity.py`가 보인 대로 **상한이 −9.6%에 불과**하다.

그러나 SDD의 진짜 주장은 단일 턴 효율이 아니라 **재작업 턴 수 감소**다.
exp04의 시뮬레이션은 기능당 71% 절감을 예측하지만 실측이 없다.
이 실험이 그 간극을 메운다.

## 1. 가설

- **H1 (주효과)**: 동일 요구 변경 3회를 반영할 때, Spec 경로의 누적 비용이
  Vibe 경로보다 30% 이상 낮다.
- **H2 (기전)**: 차이의 주원인은 단가비가 아니라 턴 수 × 이력 재전송
  (누적 입력의 N² 성장)이다.
- **H0 (기각 조건)**: 누적 비용 차이가 ±10% 이내면 "재작업 이득 없음"으로 보고한다.
  Spec 경로가 더 비싸면 그대로 보고한다 (반증 환영 — 저장소 원칙).

## 2. 설계

### 과제
카페 랜딩 페이지 (케이스 스터디와 동일 시작점).

### 두 경로 (동일 에이전트, 동일 모델, 동일 세션 조건)

| | 경로 V (Vibe) | 경로 S (Spec) |
|---|---|---|
| 시작 | 한 줄 지시 | 4필드 결정 스펙 |
| 변경 반영 | 자연어로 "바꿔줘" | 스펙 필드 수정 후 재요청 |
| 종료 조건 | 사용자(심판)가 AC 통과 판정 | AC 자동 검증 통과 |

### 요구 변경 3종 (두 경로에 동일 순서로 투입)

1. **C1 — 디자인 변경**: 팔레트를 민트/네이비로 교체, 다크모드 추가
2. **C2 — 구조 변경**: 메뉴 6종 → 8종 + 카테고리 탭, 영업시간을 히어로로 이동
3. **C3 — 요구 모순**: C1의 다크모드를 철회하고 라이트 고정 + 인쇄용 CSS 추가
   (모순 변경은 실전에서 가장 흔한 재작업 유발원)

### 측정 항목 (턴마다 기록)

| 지표 | 정의 |
|---|---|
| `tokens_in/reason/out/cache` | 턴별 사용량 (이력 재전송 포함) |
| `cumulative_cost` | GPT-5 단가 누적 비용 |
| `turns_to_pass` | 변경별 AC 통과까지 걸린 턴 수 |
| `regressions` | 변경 반영 중 기존 AC가 깨진 횟수 (품질 대리 지표) |
| `wall_clock` | 요청→통과 실제 소요 시간 ("빠르다" 주장의 최초 근거) |

### 통제

- 같은 날, 같은 모델·에이전트 버전으로 실행
- 경로 간 대화 오염 방지: 완전 분리된 세션
- Spec 작성·수정에 든 토큰도 **경로 S 비용에 산입** (공정성 — 케이스 스터디의
  한계 3번을 해소)
- 각 경로 3회 반복 (n=3), 중앙값 보고


## 4. 예측 (실행 전 기록 — 빗나가면 그대로 공개)

- 경로 V: C2·C3에서 회귀(기존 요소 파손) 발생, 총 9~14턴
- 경로 S: 총 5~7턴, 누적 비용 40~60% 절감
- 만약 경로 S가 C3(모순 변경)에서 스펙 갱신 오버헤드로 열세를 보이면,
  그것이 이 실험의 가장 가치 있는 발견이다.
