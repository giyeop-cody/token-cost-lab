# 후속 실험 설계안 — 스펙이 재작업과 전체 비용을 줄이는가

**2026-09-20 수정 초안 / 미실시. 공개 사전등록 기관에 등록된 시험이 아니다.**
본실험 전 모델·과제·표본 수·평가 기준을 고정하고 변경 이력을 남긴다.
현재 결과 칸은 의도적으로 비워 둔다. 이 문서 자체가 검증 결과는 아니다.

## 배경

현재 카페 사례는 표본 1쌍의 **usage 추정치**다. -8.3%는 지정 단가의 산술이다.
약 -9.62%는 **그 토큰 이동을 고정한 가격비 무한대 극한**이지 SDD 일반의 절감 상한이 아니다.
exp04는 cold-cache 68.7%, 예열 캐시 약 71%의 비용 시나리오이며 40→12턴 감소는 관측되지 않았다.

## 질문과 비교

- 같은 사전 정의 품질 게이트 아래, 스펙 경로의 **배정된 작업당 전체 비용**이 줄어드는가?
- 완료율과 블라인드 품질을 희생해서 싸게 중단한 것은 아닌가?
- 재작업 턴, 재전송 입력, 출력 변화가 어느 정도 기여하는가? 분해값은 단독 인과 효과로 단정하지 않는다.

경로 V: 목표를 자연어로 전달하고 변경을 반영한다.
경로 S: 같은 목표를 결정된 스펙으로 먼저 작성하고 그 스펙을 변경한다.
**두 경로 모두 같은 자동 AC + 같은 블라인드 사람 평가, 같은 종료·재시도 상한**을 적용한다.
V만 사람 심판, S만 자동 검사를 쓰면 평가 방식의 효과가 섞이므로 그렇게 비교하지 않는다.

## 표본과 실행 계획

- 초기 설계 후보: 서로 다른 웹 구현 과제 30개 × 각 3회 반복 × 2경로.
  이 크기의 검정력이 충분하다고 아직 확인한 것은 아니다. 별도 파일럿의 분산/비용으로
  실행 전 검정력과 예산을 검토하고 표본 수를 확정한다. 파일럿을 본실험 데이터에 섞지 않는다.
- 과제별 경로 실행 순서를 무작위 배정하고 시간 블록을 맞춘다. 서로 완전히 분리한 세션을 사용한다.
- 같은 모델 ID·버전·출력 상한·가격·도구·시간 상한. 캐시는 공급자가 강제 초기화되지 않을 수 있으므로
  매 요청의 read/write를 기록하고 cold/warm 상태와 순서 영향을 별도로 보고한다.
- 두 경로의 공통 요구사항은 결과를 보기 전에 고정한다. V 산출물을 본 뒤 S 스펙을 역산하지 않는다.
- 스펙 작성·수정, 하위 에이전트, compaction, 실패/절단/재시도, 캐시 저장료를 모두 비용에 넣는다.
  사람 시간과 구독료는 별도 총비용 민감도로 보고한다. 종료된 실패 작업의 지출도 누락하지 않는다.

## 품질과 통계

- 주 지표: 배정된 작업당 전체 API 비용, 완료율, 블라인드 품질 점수. 성공 작업만 골라 비용을 비교하지 않는다.
- 비용 30% 감소는 **목표 효과 크기**이지 이미 나온 결과가 아니다.
- 품질 비열등성 한계(예: 완료율 -5%p)와 시간/시도 상한은 파일럿 후 본실험 전에 고정한다.
  신뢰구간이 그 한계를 배제하지 못하면 ‘품질 유지’라고 결론내리지 않는다.
- 과제를 군집 단위로 paired bootstrap/적합한 계층 모형을 사용한다. 같은 과제 3회를 독립 문제 3개로 세지 않는다.
- 관측 비용 차이가 ±10% 이내라는 이유만으로 ‘이득 없음’이나 동등성을 확정하지 않는다.
  사전 정의한 동등성 한계와 불확실성을 함께 보고한다.
- 실패·중단·API 오류·모델 폴백은 별도 기록한다. 모두 실패한 실행을 ‘검증됨’으로 출력하지 않는다.
- 여러 주장을 검사하면 다중비교 계획을 명시한다. 외부 주장에 맞춰 채점 허용오차를 사후 변경하지 않는다.
