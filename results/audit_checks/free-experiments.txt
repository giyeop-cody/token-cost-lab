  문장 쌍 6개 · 소스: data/sentence_pairs.json

── 토크나이저별 결과 ───────────────────────────────────────────
  문장                  o200k EN/KO  배수   cl100k EN/KO  배수
  --------------------  -----------  -----  ------------  -----
  지시문 (로그인 API)       19 / 34  1.79x       19 / 52  2.74x
  추론문 (스키마 확인)      32 / 41  1.28x       32 / 70  2.19x
  설명문 (함수 동작)        20 / 25  1.25x       20 / 33  1.65x
  짧은 요약문               10 / 20  2.00x       10 / 31  3.10x
  설계 논의문               22 / 28  1.27x       22 / 47  2.14x
  에러 분석문               18 / 26  1.44x       18 / 36  2.00x
  ── 합계                 121 / 174  1.44x     121 / 269  2.22x

── 글자 수는 왜 신뢰할 수 없는가 ───────────────────────────────
  영어 토큰/글자                    0.204
  한국어 토큰/글자                  0.526   (2.58배)
  512토큰에 들어가는 글자 수        영어 2,513자  vs  한국어 973자
  → RAG 청킹을 '글자 수'로 자르면 한국어 청크만 조용히 잘려 나간다.

── 왜 이런 일이 생기는가 — 실제 분해 ───────────────────────────
  '에이전트'                        4토큰   [에/이/전/트]
  ' agent'                          1토큰   [ agent]
  '데이터베이스'                    4토큰   [데/이터/베/이스]
  ' database'                       1토큰   [ database]
  '인증'                            2토큰   [인/증]
  ' auth'                           1토큰   [ auth]
  → o200k 어휘 20만개 중 한글은 약 1.2%. 자리가 없어 잘게 쪼개진다.

  주장   : ① 한국어 추론은 영어보다 비싸다
  판정   : 참 (단, 배수는 토크나이저에 따라 다름)
  근거   : 최신 o200k에서도 1.44배, 구형 cl100k에서는 2.22배. Claude 토크나이저는 외부 측정 기준 1.88배로 더 나쁨.

  ⚠️ 반례도 있다: 모델·언어·과제별 효과가 다르다. 생성 길이와 정확도를 각각 확인해야 한다.
     → 배수는 '자기가 쓰는 모델'로 직접 재라. 이 스크립트가 그 용도다.

── D. 손익분기 — 입력을 얼마나 더 써도 되는가 ──────────────────
  Claude Sonnet 4.6 기준, 출력 1토큰 = 입력 5.0토큰과 같은 값.
    출력 500토큰을 줄일 수 있다면 → 입력을 2,500토큰까지 더 써도 본전.
    출력 1,000토큰을 줄일 수 있다면 → 입력을 5,000토큰까지 더 써도 본전.
    출력 3,000토큰을 줄일 수 있다면 → 입력을 15,000토큰까지 더 써도 본전.
    출력 5,000토큰을 줄일 수 있다면 → 입력을 25,000토큰까지 더 써도 본전.
  캐시에 올린 입력이라면 여유는 50배로 커진다 (출력 1,000tok ↔ 캐시입력 50,000tok).
  → '스펙을 길게 쓰면 입력이 늘어서 손해 아닌가?' 라는 반론에 대한 답이다.

  → 위 히트율은 민감도 가정이다. 실제 비율은 자기 usage 로그로 측정한다.

── D. 손익분기 — 쓰기 프리미엄은 몇 콜 만에 회수되나 ───────────
  쓰기 추가 비용                    $0.0150

── E. 안티패턴 — 캐시를 깨뜨리는 한 줄 ─────────────────────────
  프롬프트 맨 앞에 '현재 시각: 2026-08-14 09:31:07' 같은 값을 넣으면
  프리픽스가 매번 달라져 캐시가 전혀 매칭되지 않는다.
  올바른 배치 (동적 값 뒤)          $3.22
  잘못된 배치 (동적 값 앞)          $10.05   → 3.1배, +$6.83
  ⚠️ 쓰기 프리미엄까지 매번 물기 때문에 캐시를 아예 안 쓴 것보다 비쌀 수 있다.

── F. 체크리스트 ───────────────────────────────────────────────
  1. 시스템 프롬프트·툴 정의·코딩 규약·레퍼런스 문서를 맨 앞 고정 블록으로 모은다
  2. 타임스탬프·요청ID·사용자 입력 등 변하는 값은 반드시 맨 뒤로 보낸다
  3. 고정 블록이 해당 모델의 최소 토큰 조건을 넘는지 확인한다 (Haiku 4.5: 4,096)
  4. 툴 정의를 자주 바꾸지 않는다 (툴 1개당 스키마 100~1,000토큰)
  5. 응답의 cache_read_input_tokens / cache_creation_input_tokens 를 대시보드로 본다
  6. 히트율이 50% 아래면 프롬프트 앞부분에 변동 요소가 있는지 의심한다

  주장   : 프롬프트 캐싱은 실제로 큰 절감을 준다
  판정   : 조건부 시나리오 — 실제 히트율/TTL/품질은 별도 측정
  근거   : Claude Sonnet 4.6 · 프리픽스 20,000tok · 100콜 기준 62% 절감. 앞선 동적값이 해당 프리픽스를 깨뜨리면 미스 비용이 생길 수 있다. 캐시 지점·범위를 함께 본다.

========================================================================================
  실험 04 — 에이전트 루프의 2차 함수 비용과 SDD (주장 ②·④)
========================================================================================
  모델                              Claude Sonnet 4.6
  고정 프리픽스                     8,000 tok
  턴당 신규 입력 / 출력             2,000 tok / 800 tok

── A. 왜 2차 함수인가 — 턴이 늘수록 입력이 눈덩이 ──────────────
  턴 수  누적 입력tok  총비용  턴당 평균
  -----  ------------  ------  ---------
      5        68,000   $0.26    $0.0528
     10       206,000   $0.74    $0.0738
     20       692,000   $2.32    $0.1158
     30     1,458,000   $4.73    $0.1578
     50     3,830,000  $12.09    $0.2418
  → 턴을 2배(10→20)로 늘리면 비용은 3.1배가 된다. 2배가 아니다.
     '한 번 더 물어보지 뭐'가 싼 행동이 아닌 이유.

── B. 재작업 사이클이 만드는 총비용 차이 ───────────────────────
  턴 수 40→12는 측정 결과가 아니라 입력 가정이다. 별도 스펙 작성 토큰 비용 포함.
  사이클별 초기 캐시: cold, 첫 쓰기 비용 포함
  접근     재작업 사이클  총 턴  스펙tok  기능당 비용  차이
  -------  -------------  -----  -------  -----------  ------
  vibe                 5     40        0        $1.89   +0.0%
  shallow              3     24    1,500        $1.19  -36.9%
  sdd                  2     12    4,000        $0.59  -68.7%
  ⚠️ 스펙 작성 토큰 비용은 포함. 실제 턴 감소·품질 동등성·사람 시간은 미검증.
     이 가정에서의 절감은 주로 줄어든 턴 수 때문이다. 인과 검증은 별도 실험이 필요하다.

── C. 컨텍스트 관리 기법을 얹으면 ──────────────────────────────
  20턴 세션 전략          총비용  절감  비고
  ----------------------  ------  ----  -----------------------------------
  아무것도 안 함           $2.32  기준  —
  프롬프트 캐싱만          $1.91  +17%  프리픽스만 절감. 이력 누적은 그대로
  캐싱 + 10턴마다 컴팩션   $1.23  +47%  요약 콜 비용 포함
  캐싱 + 5턴마다 컴팩션    $0.93  +60%  너무 잦으면 요약 콜이 비용을 먹는다
  → 컴팩션 주기에는 최적점이 있다. 무조건 자주 접는다고 싸지지 않는다.
     주기별 손익은 요약 비용과 품질·재작업 변화를 함께 측정해야 한다.

── D. YAGNI — 안 쓸 기능의 값 ──────────────────────────────────
  '나중에 필요할 것 같아서' 만든 코드는 생성 비용 + 매 턴 재전송 비용을 물린다.
  범위                    추가 코드tok  생성 비용  20턴 재전송  합계
  ----------------------  ------------  ---------  -----------  ------
  필요한 것만                        0     $0.000       $0.000  $0.000
  추상화 레이어 3개 추가         3,600     $0.054       $0.216  $0.270
  플러그인 시스템까지            7,200     $0.108       $0.432  $0.540
  → 안 쓰는 코드는 한 번 비싼 게 아니라, 세션이 끝날 때까지 계속 과금된다.

  주장   : ②·④ 스펙을 먼저 쓰고 범위를 줄이면 토큰이 절약된다
  판정   : 조건부 시나리오 — 실제 턴 감소는 미측정
  근거   : 에이전트 비용은 턴 수의 2차 함수다. 턴 10→20이면 비용은 3.1배. 스펙이 실제 재작업 사이클을 줄인다면 이 누적을 줄일 수 있다.

  ⚠️ 반대 증거도 있다:
     · ETH Zurich 연구 — LLM이 생성한 컨텍스트 파일은 성공률을 살짝 떨어뜨리면서
       전체 에이전트 비용을 늘린 조건이 있다 (+20%/+23%, v1). 개발자 파일도 비용은 늘 수 있다.
     · 외부 블로그 두 사례: Spec-Kit은 OpenSpec 대비 +97~109%. 둘 다 SDD이며 본 저장소의 재현 아님.
     → 결론: '스펙을 쓰라'가 아니라 '짧고 결정만 담은 스펙을 쓰라'.
       설명(description)이 아니라 결정(decision)을 적을 것.

========================================================================================
  실험 09 — DRY를 토큰 경제로 번역하면
========================================================================================
  모델                              Claude Sonnet 4.6   (입력 $3.0/1M · 출력 $15.0/1M · 캐시읽기 0.1x)

── A. 같은 코드 재작성 최소화 ──────────────────────────────────
  방식              1회 출력  10회 누적  비용
  ----------------  --------  ---------  -------
  파일 전체 재출력     5,000     50,000  $0.7500
  바뀐 부분만 출력       300      3,000  $0.0450

  절감                              94%   (연 1760회 기준 $124)
  → '전체 파일을 다시 써줘'가 가장 비싼 한마디다.
     같은 코드를 두 번 만들지 않는 것 = 출력 토큰을 두 번 사지 않는 것.

── B. 반복되는 컨텍스트 최소화  ← 처방이 틀린 항목 ─────────────
  전략                       입력 토큰  비용     절감
  -------------------------  ---------  -------  ----
  ① 매번 그대로 전송         1,200,000  $3.6000  기준
  ② 절반으로 요약·삭제         600,000  $1.8000   50%
  ③ 그대로 두고 캐싱         1,200,000  $0.4014   89%
  ④ 압축 + 고정 + 캐싱         600,000  $0.2007   94%
  ⑤ 앞에 동적값 → 매번 미스  1,200,000  $4.5000  -25%

  ★ 압축과 캐싱은 함께 적용할 수 있다. 압축 비용·품질 손실·TTL은 이 계산 밖이다.
     ② $1.8000  vs  ③ $0.4014  →  4.5배 차이

  코드의 DRY는 '중복을 지워라'다. 토큰의 DRY는 다르다:
    지울 수 있는 반복은 지우고,
    지울 수 없는 반복은 **한 글자도 바꾸지 말고 고정**해서 캐시에 태운다.
    적은 반복이 아니라 '변주(variation)'다.

  ④가 그 증거다. 같은 12,000토큰을 보내면서 앞에 타임스탬프 하나 붙였을 뿐인데
    아무것도 안 한 ①보다 25% 더 낸다.

── C. 반복되는 리워크 최소화 ───────────────────────────────────
  리워크                 누적 턴  비용     1사이클 대비
  ---------------------  -------  -------  ------------
  1사이클 (스펙 있음)        8턴  $0.1908             -
  2사이클                   16턴  $0.5160         2.7배
  4사이클 (감으로 시작)     32턴  $1.5696         8.2배
  6사이클                   48턴  $3.1608        16.6배

  6사이클 / 1사이클                 16.6배   턴이 6배면 비용은 6배가 아니다
  → 리워크는 '한 번 더 시키는 것'이 아니라, 그때까지의 대화 전체를
     다시 사기 시작하는 것이다. 이력이 매 턴 재전송되기 때문.

── D. 같은 로직은 한 군데서 ────────────────────────────────────
  구조           입력    출력   5회 수정 비용
  -------------  ------  -----  -------------
  단일 출처 1곳   4,000  1,500        $0.0345
  복붙 3곳       12,000  4,500        $0.1035

  복제의 대가                       3.0배   (복제 수 3에 정비례)
  → 복붙은 만들 때가 아니라 **고칠 때마다** 청구된다.
     게다가 한 곳만 고치고 두 곳을 놓치면 그 디버깅이 또 리워크(C)다.

── E. 같은 프롬프트는 최소화  ← 두 가지가 섞여 있는 항목 ───────
  상황                           실제 호출  비용     절감
  -----------------------------  ---------  -------  ----
  중복 30%를 그냥 다 호출           10,000  $135.00     -
  의미 동일 → 시맨틱 캐시 히트       7,000   $94.50   30%
  같은 질문, 표현만 다름 → 미스     10,000  $135.00    0%

  이 항목은 두 개가 섞여 있다. 분리해야 한다:
    · 중복 '호출'  → 없애라. 답이 같은 질문을 두 번 사지 마라. (-30%)
    · 중복 '내용'  → 없애지 말고 **똑같이 고정**하라. 캐시가 할인해준다.

  둘 다 적이 같다: '거의 같지만 미묘하게 다른 것'.
  캐시는 완전 일치에만 반응하므로, 어중간한 변주가 가장 비싸다.

── 판정 ────────────────────────────────────────────────────────
  #  DRY 항목                  판정    근거
  -  ------------------------  ------  -------------------------------------------------------
  A  같은 코드 재작성 최소화   참      전체 재출력 대비 -94%
  B  반복되는 컨텍스트 최소화  조건부  압축+캐싱 병용 가능; 원문 캐싱만도 -89% (기본 시나리오)
  C  반복되는 리워크 최소화    참      6사이클은 1사이클의 16.6배
  D  같은 로직은 한 군데서     참      복붙 3곳 = 수정 비용 3배
  E  같은 프롬프트는 최소화    조건부  중복 호출은 제거, 중복 내용은 고정

  주장   : DRY를 지키면 토큰이 절약된다
  판정   : 참 — 단, 코드의 DRY와 컨텍스트의 DRY는 처방이 반대다
  근거   : 코드·로직·리워크의 중복은 '제거'가 답이다(A·C·D). 그러나 시스템 프롬프트처럼 제거할 수 없는 반복은 '고정'이 답이다(B·E). 토큰 경제에서 비싼 것은 반복이 아니라 변주다. 똑같이 반복되면 캐시가 90%를 깎아주지만, 변경 지점 이전의 캐시 가능한 공통 프리픽스는 남을 수 있다.
