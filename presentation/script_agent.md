## 3. 네 가지 원칙은 그대로 쓴다

## 5. A와 B는 다른 실패를 처리한다

**내부 AC 실패 / 사용자 반려** · 참조 정책

- A: 테스트가 검출한 실패를 턴 안에서 처리.
- B: 사용자 반려를 의도 이력과 함께 판정.
- 검출할 AC가 부실하면 A가 놓친다. 문자열 검사만으로 기능을 보증하지 않는다.

## 12. API usage를 다룰 때의 세 가지 규칙

**캐시를 두 번 빼지 않는다** · 공식 스키마 + mock 회귀

- Gemini promptTokenCount는 캐시 입력을 포함. cost()에 전체 prompt와 cached를 전달.
- Gemini Content는 role + parts. 모델 응답의 thoughtSignature와 functionCall id를 보존.
- 툴 내용은 두 번째 요청에서 처음 입력되고 세 번째 요청에서 재전송된다.
- 요청 실패·절단·키 없음은 미검증/실패로 기록. 3벤더 ‘확인됨’을 미리 출력하지 않는다.

근거: `experiments/exp10_thinking_cross_vendor.py · exp11_tool_output_bloat.py`

## 13. 캐시 적격성은 모델별로 다르다

**Haiku 4.5: 최소 4,096 토큰** · 공식 조건 + 경계값 회귀 테스트

- Sonnet 4.6: 1,024 / Opus 4.6: 4,096 (공식 문서 확인일 2026-09-20)
- 짧은 프리픽스를 1K 공통 규칙으로 할인하지 않는다. 미확인 기준은 ‘미확인’으로 둔다.
- 적격성 충족은 히트 보장이 아니다. 실제 cache usage·TTL·쓰기/저장료를 본다.

근거: `platform.claude.com/docs/en/build-with-claude/prompt-caching`

## 14. 캐싱의 손익은 조건으로 재현한다

## 16. SDD 절감은 ‘턴 감소’ 가정에 달린다

**기존 71.0% / cold-cache 68.7%** · SDD 비용 시나리오

- 40턴 → 12턴은 모델의 입력 가정. 스펙이 실제 이만큼 줄였다는 관측은 없다.
- 스펙 작성: 입력 3,000 + 출력 4,000 비용을 이미 포함한다.
- 기존 약 71%는 캐시 예열 비용 제외. 기본은 사이클별 첫 쓰기까지 포함한다.
- 주장 유지: 짧고 결정적인 스펙을 우선 시도하되 재작업·품질·총비용으로 검증한다.
