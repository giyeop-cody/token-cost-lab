## 1. 🔴 치명적 오류

### 1-1. 슬라이드 25 "답변은 여섯 번 다 같은 숫자" — **사실이 아니다**

덱과 스크립트의 감정적 클라이맥스이자, 질문받기 가장 쉬운 지점이다.
`results/thinking_sweep.jsonl` 30행의 `text` 필드를 그대로 집계하면:

| 예산 | 실제 응답 문자열 분포 | 정답률(±0.05) |
|---|---|---|
| 미지정 | `38.016` ×6 | 6/6 |
| 끔(0) | `38.016` ×3, `$38.016` ×2, **`380.16` ×1** | 5/6 |
| 512 | `$37.32` `40.13` `$42.24` `$38.02` `$40.32` `$38.016` 전부 다름 | **2/6** |
| 2048 | `38.016` ×4, `37.9944` ×2 | 6/6 |
| 자동(−1) | `38.016` ×1, `$38.016` ×2, `37.9944` ×3 | 6/6 |

- 문자열이 동일한 조건은 **미지정 하나뿐**이다.
- 사고를 **끈** 조건에서 `380.16`(10배 자릿수 오류)이 1회 나왔다. 슬라이드는 "사고를 끄면 정확하다"는
  인상을 주지만 데이터는 그렇게 말하지 않는다.
- `37.9944`는 오답이 아니라 **1,760이 아닌 1,759회로 계산한 off-by-one**이다
  (`1759/1760 × 38.016 = 37.9944`). 정답 범위로 처리하는 게 맞지만, "같은 숫자"는 아니다.

**해결:** 표의 마지막 열을 응답 문자열이 아니라 **정답률(n/6)**로 교체했다. 논지는 오히려 강해진다 —
"문자열이 같다"는 우연에 의존하지만, **"사고를 꺼도 켜도 정답률 6/6인데 요금만 240배"**는
품질 대비 비용이라는 정확한 주장이 된다. 스크립트에는 질문 대비 답변을 추가했다.

### 1-2. 슬라이드 25 "512는 오답을 냈다" — 표본을 1개만 보여줬다

슬라이드는 6회 중 첫 번째 값 `$37.32`만 뽑아 "← 오답"으로 표시했다. 실제로는 **6회 중 4회가 오답**
(37.32 / 40.13 / 42.24 / 40.32)이다. 우연한 1회 실패로 보이지만 실은 **정답률 33%로의 붕괴**다.

**해결:** "정답 2/6 ← 품질 붕괴"로 교체. 원래 주장보다 훨씬 강한 근거인데 약하게 쓰고 있었다.

### 1-3. 슬라이드 2 단위 오류 — 10배

> "같은 **1,000 토큰**이라도 캐시된 입력이면 0.3센트, 생성된 출력이면 15센트"

Sonnet 단가($3/$15 per 1M)로 1,000토큰을 계산하면 캐시 입력 **0.03센트**, 출력 **1.5센트**다.
0.3센트/15센트가 되려면 **10,000토큰**이어야 한다. 50배라는 비율은 맞지만 절대값이 전부 10배 틀렸다.
발표 두 번째 장에 나오는 숫자라 초반에 신뢰를 잃을 수 있다.

**해결:** "10,000 토큰"으로 수정 (덱·스크립트 양쪽).

## 2. 🟠 중대 오류

### 2-1. 슬라이드 5 — 표에 행이 하나 빠졌다

"합계 **(6문장)** 121 / 174 / 269"인데 표에는 **5행만** 있었다. 5행을 더하면 103 / 148 / 233으로
합계와 맞지 않는다. `data/sentence_pairs.json`과 대조하니 **"에러 분석문"(18 / 26 / 36)**이 누락돼 있었다.
합계 숫자 자체는 정확했다 — 표시만 빠진 것이다. 청중이 암산하면 바로 걸린다.

**해결:** 누락 행 복원. 이제 5행 합이 합계와 정확히 일치한다.

### 2-2. 슬라이드 17 — 기준선이 슬라이드 16과 다르다

슬라이드 16은 "캐시 없음 $8.55 → 캐시 $3.22 = 62% 절감"인데,
슬라이드 17은 같은 조건에서 "0% (캐시 미사용) $10.05"를 기준으로 삼고 절감률을 -27/-54/-65/-68%로 표기했다.

$10.05는 **캐시를 미사용한 비용이 아니라, 캐싱을 켰는데 매번 미스가 난 비용**이다(쓰기 프리미엄 1.25배를
매번 지불). 진짜 미사용은 $8.55다. 잘못된 기준 탓에 절감률이 전부 과대 표기됐고, 두 슬라이드가
1분 간격으로 62% vs 68%라는 다른 숫자를 말하게 된다.

**해결:** 기준선을 $8.55로 통일하고 $10.05는 "0% — 켰는데 매번 미스 **+18%**"라는 별도 경고 행으로 분리.
절감률은 -14 / -46 / -58 / **-62%**로 정정 — 슬라이드 16과 일치한다.
덤으로 안티패턴의 위험이 더 선명해졌다: **캐싱을 잘못 켜면 안 켠 것보다 18% 비싸다.**

### 2-3. 240배는 단가 가정에 의존한다 — 명시가 없었다

`thinking_sweep.py`는 실제로는 `gemini-3.1-flash-lite`를 호출하고, 비용은 `gemini-25`($1.25/$10)
단가로 환산한다. 실제 flash-lite 공식 단가로 계산하면 **약 149배**다. 토큰 수 자체의 배수는 618배다.
`LIVE_RESULTS.md` 서두에는 "비율만 보라"는 주의가 있지만 **슬라이드·스크립트에는 없다.**
"실측"이라고 강조한 장이라 단가 가정이 숨어 있으면 타격이 크다.

**해결:** 슬라이드 24 각주와 스크립트 질문 대비, `LIVE_RESULTS.md` §8에 단가 전제를 명시.

### 2-4. 슬라이드 8 "Latin 59.5%, 한글 1.2%" — 출처 불명, 절반만 맞다

o200k_base 20만 어휘를 직접 스캔한 결과:

| 항목 | 슬라이드 | 실측 |
|---|---|---|
| 한글 포함 토큰 | 1.2% | **1.19% ✅** |
| 라틴 문자 포함 토큰 | 59.5% | **67.2%** (순수 영문+공백만 세면 53.0%) |

한글 1.2%는 정확하다. 라틴 59.5%는 어떤 집계 기준으로도 재현되지 않았고, "GPT-5 계열"이라는
모델 귀속도 근거가 없다(o200k는 GPT-4o 계열 토크나이저).

**해결:** "o200k 20만 어휘 중 라틴 문자 포함 토큰 67%, 한글 포함 토큰 1.2% (자체 실측)"으로 교체.
검증 가능한 문장으로 바뀌었고 논지(한글에 자리가 없다)는 그대로다.

## 5. ✅ PDF 재생성 완료

LibreOffice를 설치하고 **`make_pdf.py`(신규)**로 변환했다. 단순 `soffice --convert-to pdf`가
아니라, 이 덱 특유의 함정을 처리한다:

- **폰트 치환** — 덱은 `맑은 고딕`(Windows 전용) 기준이다. 그대로 변환하면 LibreOffice가
  임의 폰트로 대체해 글자 폭이 달라지고 표가 넘친다. fontconfig 별칭으로
  `맑은 고딕→NanumGothic`, `Consolas→NanumGothicCoding`을 명시적으로 매핑한다.
  (시스템 `fonts.conf`를 `<include>`하지 않으면 LibreOffice가 폰트를 하나도 못 찾는다 —
  이 함정도 스크립트에 주석으로 박아 두었다.)
- **변환 검증** — `--check`로 PDF 쪽수(28) = PPTX 장수(28), 한글 텍스트 추출 가능 여부
  (이미지로만 구워졌는지 확인), 수정 사항 3종의 실제 반영을 자동 확인한다.

```bash
python make_pdf.py --check
```

### 6-1. 🆕 `tools/verify_deck.py` — 수치 회귀 검사기 (96개 검사)

이번 검증에서 발견한 12건 중 7건은 "원자료는 맞는데 슬라이드가 다른 말을 하는" 유형이었다.

```bash
python token-cost-lab/tools/verify_deck.py     # 실패 시 exit 1 → CI에 바로 연결 가능
```

검사 범주:

| 검사 | 잡는 오류 유형 | 이번에 대응하는 건 |
|---|---|---|
| 원자료 재계산 vs 슬라이드 표기 | 수치 불일치 | 슬라이드 7·25 전체 |

| 표 행 합계 = 표기 합계 | 행 누락 | 중대 2-1 |
| 슬라이드 간 기준선 일관성 | 같은 지표 다른 값 | 중대 2-2 |
| 단가 민감도 | 가정 은폐 | 중대 2-3 |
| 단위 검사 | 자릿수 오류 | 치명 1-3 |
| 참조 파일 존재 | 없는 파일 안내 | 경미 3-2 |
| 덱 텍스트 금칙어 | 수정 전 문구 잔존 | 재발 방지 |

**동작 확인:** 고친 오류를 일부러 되살려 두 방향 모두 검출됨을 확인했다.
(a) 덱에 옛 문구 재삽입 → `✗ 덱에 수정 전 문구 없음` (b) 원자료의 오답을 정답으로 조작 →
`✗ 정답률 2/6 — 재계산 3/6`. 통과만 하는 테스트는 테스트가 아니다.

> 설계 원칙 하나: 검사기는 `exp04`를 **재구현하지 않고 임포트**한다.
> 처음엔 루프 비용을 직접 계산했다가 $2.44 vs $2.32로 어긋났는데, **덱이 아니라 검사기가 틀렸다.**
> 검사기가 자기만의 계산식을 들고 있으면 그게 또 하나의 진실 공급원이 된다.

### 6-2. 단가 이중 표기 (제안 #2)

`pricing.py`에 실제 호출 모델 `flash-lite`($0.10/$0.40)를 추가하고,
`thinking_sweep.py` 요약에 민감도를 자동 출력하게 했다.

```
[단가 민감도] 위 배수는 gemini-25($1.25/$10) 환산 기준이다.
실제 호출 모델의 공식 단가($0.10/$0.40)로 계산하면 149×.
→ 인용할 때 '어느 단가 기준인지'를 반드시 함께 말할 것.
```

### 6-3. p값 표기 정정 (제안 #3)

`p = 0.00e+00`은 언더플로일 뿐 "p가 0"이 아니다. `< 1e-16 (정규근사 한계)`로 바꿨다.
`results/stats_thinking.txt` 재생성 완료.

### 6-4. 정답률 Wilson 신뢰구간 (제안 #1)

`thinking_sweep.py`가 정답률을 **Wilson 95% CI와 함께** 출력한다.

```
512      2/6  [10–70%]
자동(-1) 6/6  [61–100%]
```

**구간이 겹친다** — n=6으로는 "512가 유의하게 나쁘다"고 말할 수 없다는 뜻이다.
이 한계를 스크립트 질문 대비와 `LIVE_RESULTS.md`에 명시했다. 반면 비용 배수는
분산이 거의 없어 이 한계와 무관하게 견고하다.

### 6-5. 요약 도구 자체의 과장 제거

`thinking_sweep.py`의 기본 출력이 "최종답변" 열과 **"눈에 보이는 답변은 동일한데"**라는
문구를 쓰고 있었다. 애초에 치명 오류 1-1이 여기서 나왔다. 열을 **정답률**로 바꾸고,
"응답 문자열까지 동일한 것은 아니다"라는 주의를 출력에 넣었다.
**도구가 정직해야 문서가 정직해진다.**
