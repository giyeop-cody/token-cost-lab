# 사다리 A + B — 어디서, 어떻게, 어떻게 자동화하나

- 구현: `agent_setup/orchestrator.py`
- 검증: `agent_setup/test_orchestrator.py` (14/14)
- 자동화 표면: `agent_setup/mcp_server.py`의 **`user_turn`** 도구

---

## 1. 결론부터 — "합친다"는 칸을 이어 붙이는 게 아니다

두 사다리는 **다른 시간축**에서 돈다.

| | A | B |
|---|---|---|
| 도는 시점 | **턴 내부** (사용자는 안 봄) | **사용자 턴 경계** |
| 한 바퀴 비용 | 싸다 (출력 900 상한) | 비싸다 (출력 2500 전액) |
| 태우는 것 | 토큰만 | **사용자의 시간** |

그래서 결합은 **A의 칸 뒤에 B의 칸을 붙이는 것**이 아니라,
**A를 B 안쪽에 중첩시키는 것**이다.

```
┌─ 사용자 턴 ──────────────────────────────────────────┐
│ B: 이 명령이 직전 의도의 반복인가?                    │
│    ├ 새 의도 → A 초기화 + 첫 배정                     │
│    ├ 반복    → B 한 칸 (A의 티어를 물려받아 시작)      │
│    └ 소진    → respec, 사람에게                       │
│                                                       │
│  ┌─ 턴 내부 (사용자는 못 봄) ──────────────────────┐  │
│  │ A: AC 실패 → 한 칸 → 재실행 → AC 실패 → ...     │  │
│  │    AC 통과 또는 max_attempts까지 반복           │  │
│  └─────────────────────────────────────────────────┘  │
│ 결과물 전달 → (틀렸으면 다음 턴에 B가 잡는다)          │
└───────────────────────────────────────────────────────┘
```

**A가 안쪽인 이유**: 싼 쪽이 먼저 여러 번 돌아야 한다. B는 한 칸당
사용자 턴 하나를 태우므로 가장 바깥에서 최소 횟수만 돌아야 한다.

## 2. 어디서 쓰나 — 실패 종류별 담당

| 실패 종류 | 감지 | 담당 |
|---|---|---|
| 테스트/AC 실패 | 에이전트 자신 | **A** |
| 린트·타입·빌드 깨짐 | CI | **A** |
| 배치·비동기 작업 실패 | 워커 | **A** (B는 못 봄) |
| **AC는 통과인데 의도와 다름** | 사용자 반려 | **B** (A는 영영 못 봄) |
| 같은 요청 7회 반복 | B 사다리 소진 | **respec → 사람** |

두 사다리가 놓치는 실패가 정반대라 **둘 다 필요**하다.
A만 쓰면 "테스트는 초록인데 원하는 게 아닌" 결과가 그대로 나간다.
B만 쓰면 모든 실패가 사용자 턴을 태우고, 배치 실패는 방치된다.

## 3. 결합할 때 반드시 지켜야 할 규칙 3개

구현하면서 실제로 버그를 만든 지점들이다.

### ① B는 A가 도달한 티어 아래로 내려가지 않는다 (`tier_floor`)

A가 LARGE까지 올라가 AC를 통과시킨 결과물을 사용자가 반려했다면,
B의 1번 칸이 MID라고 해서 MID로 돌아가는 건 **명백한 퇴보**다.
이미 알아낸 난이도 정보를 버리는 것이기 때문이다.

```
A: mid → mid → large (AC 통과) → 전달 → 사용자 반려
B: 1번 칸은 원래 mid …이지만 large로 시작  ← tier_floor가 막는다
```

### ② B가 돌면 A의 실패 카운트는 리셋된다

B가 돈다는 건 A가 "성공했다"고 **잘못 판정하고 빠져나왔다**는 뜻이다.
B가 새 범위·새 티어를 깔았으므로, A는 그 새 조건에서 처음부터 센다.
안 그러면 A가 남은 카운트만으로 조기 소진된다.

### ③ 새 의도가 오면 둘 다 초기화한다

앞 작업의 난이도를 다음 작업에 물려주면, 쉬운 작업이 LARGE로 간다.

## 4. 구현 중 잡은 버그 — 앵커

이게 없으면 결합이 **조용히 무너진다**.

`IntentTracker`는 원래 **직전 명령**과 비교했다. 그런데 사람은 재요청을
점점 짧게 줄인다:

```
"결제 실패 재시도 로직 구현해줘"   ← 내용어 4개
"결제 재시도 부분 다시 좀 해줘"     ← 내용어 3개
"이거 다시"                        ← 내용어 0개  ★
"아직도 아니야 결제 재시도 다시"    ← 이걸 "이거 다시"와 비교하면 유사도 0
```

`"이거 다시"`는 내용어가 **0개**라, 그 다음 턴은 **비교 대상이 비어**
새 의도로 오판된다. 실제로 결합 실행기에서 이 현상이 재현됐다 —
6번째 턴에서 사다리가 통째로 초기화되고 티어가 large에서 mid로 떨어졌다.

**수정**: 직전 명령이 아니라 **앵커**(이 의도 묶음을 시작한, 내용 있는
명령)와 비교한다. 앵커는 생략형으로는 갱신하지 않는다.

수정 후 8턴 시나리오가 7칸을 온전히 완주하고, 결합 상한이
**$0.5149**로 B 단독 상한과 정확히 일치한다(테스트로 고정).

## 6. 자동화 — MCP 도구 하나로

라우팅 훅은 공개돼 있지 않다. 에이전트에 끼워 넣는 **유일한 실용 경로는
MCP 도구**이므로, 결합 실행기를 `user_turn` 도구로 노출했다.
서버 도구는 5개 → **6개**가 됐다.

### 에이전트가 지켜야 할 호출 순서

```
사용자 명령 도착
   └─ user_turn(task_id, command)      ← 반드시 가장 먼저
        ├ layer=A → 배정된 tier로 첫 구현
        └ layer=B → instruction대로 재작업
                     (같은 범위로 다시 만들지 말 것)
   └─ 구현 → 테스트
        └ 실패하면 rework_next(task_id, failure)  ← 턴 내부 반복
   └─ AC 통과 → 결과 전달
```

`user_turn`은 판정만 하지 않고 **행동 지시문**을 함께 낸다.
B가 걸리면 이런 문장이 붙는다:

> 사용자가 같은 의도를 반복했다 — 사용자가 결과를 보고 다시 시켰다.
> 같은 범위로 또 하면 같은 결과가 나온다. / 같은 범위로 다시 만들지
> 말 것. 앞 결과물의 어느 부분이 의도와 어긋났는지 먼저 짚고 시작할 것.

리셋 칸에서는 여기에 "새 세션에서 시작 — 범위는 unit으로 되돌리되
모델 티어는 유지한다"가 추가된다.

### 강제력의 한계 — 정직하게

MCP 도구는 **에이전트가 호출해야** 동작한다. 모델이 `user_turn`을 건너뛰면
사다리는 돌지 않는다. 완전한 강제는 불가능하고, 실무에서는 두 겹으로 건다:

1. `AGENTS.md`에 "사용자 명령마다 `user_turn` 먼저" 규칙 명시
2. 툴 응답의 `instruction` 필드로 다음 행동을 좁게 지정

구조적으로 확실한 지점은 **출력 상한**(`trim_explain`)처럼
호출하면 반드시 걸리는 것들이다. 사다리는 그보다 약한 규율이다.
