## 1. 케이스 — "AC 16/16 통과"인데 의도와 어긋난 것이 실제로 있었다

`intent_guard.md`에서 **논증**으로만 주장했던 "AC는 의도의 부분집합"이
이 케이스에서 **실물로 확인**됐다.

`verify_ac.py` 결과는 **16/16 PASS**. 게이트는 초록불이다.
그런데 두 산출물의 **사용자 가시 텍스트**를 전수 대조하면 5건이 사라져 있다.

| 사라진 문구 | 성격 | 이걸 잡는 AC |
|---|---|---|
| `카페 온도 — 따뜻함을 내리는 곳` | 브랜드 카피(eyebrow) | **없음** |
| `수원 행궁동 · 매일 로스팅` | 위치 서브카피 | **없음** |
| `매일 아침 로스팅한 원두, 국산 재료로 만드는 디저트` | 소개 문구 | **없음** |
| `09:00 – 21:00 (L.O 20:30)` | **라스트오더 시각** | **없음** |
| `10:00 – 22:00 (L.O 21:30)` | **라스트오더 시각** | **없음** |

### 왜 AC5가 이걸 못 잡았나 — 검사식을 뜯어보면

```python
add("AC5 영업시간 명시",
    "09:00 – 21:00" in html and "10:00 – 22:00" in html and "첫째 주 월요일" in html)
```

**부분문자열 검사**다. `09:00 – 21:00`만 있으면 통과한다.
뒤에 붙어 있던 `(L.O 20:30)`이 통째로 증발해도 게이트는 초록불이다.

- VIBE 산출물: AC5=True, `L.O` 포함 **True**
- SPEC 산출물: AC5=True, `L.O` 포함 **False**

**카페에서 라스트오더는 영업시간만큼 중요한 정보다.** 손님이 20:50에 오면
헛걸음한다. AC는 통과했고, 사람은 아무도 반려하지 않았고, 정보는 사라졌다.

> 이 케이스가 증명하는 것: 결함은 "AC를 안 지켜서"가 아니라
> **"AC가 안 물어봐서"** 생긴다. 모델 티어를 올려도 안 잡힌다 —
> LARGE 모델도 스펙에 없는 것을 지킬 의무는 없다.

### 분류기에 태우면

반려 발화 `"영업시간에서 라스트오더 표기가 빠졌다. 원래 있던 건데 왜 없어졌나"`

```
→ 숨은 전제(assumption)   근거='원래'
→ 대응칸 = widen,  티어상승 = 불필요
→ 처방: 전제를 AC로 승격 — 다음부터 자동 검사
```

분류기가 **티어를 올리지 말라**고 정확히 판정한다. 처방도 맞다 —
`verify_ac.py`에 `"L.O" in html` **한 줄**($0)을 넣으면 영구히 재발하지 않는다.
B 사다리 1칸은 $0.0286이다.

## 2. 실로그 재생 — 분류기 40%, **B 사다리 감지기 0/5**

페르소나 A의 반려 5턴을 그대로 태운 결과.

| 턴 | 실제 발화 | 분류 | 판정 |
|---|---|---|---|
| 2 | 아니 이렇게 복잡한 거 말고... 그냥 html 파일 하나로 되는 거 | **unknown** | ✗ |
| 3 | 디자인이 너무 밋밋한데 다크 테마로 해줘 | taste(`디자인`) | ○ |
| 4 | 저장이 안 되는 것 같은데? 새로고침하면 사라져 | **unknown** | ✗ |
| 5 | 이제 저장은 되는데 목록에서 클릭해도 안 열려 | **unknown** | ✗ |
| 6 | 음... 그냥 처음부터 심플하게 다시 만들어줘. 이벤트버스 이런 거 다 빼고 | scope(`빼고`) | ○ |

**분류 성공 2/5 = 40%.** 개발자 예문으로 만든 24/24 PASS와 실로그는 다르다.

### 더 심각한 것 — B 사다리가 한 칸도 안 올라간다

같은 6턴을 `IntentTracker`에 태우면 **에스컬레이션 0/5**, 최종 칸 0, 티어 MID 고정.
5턴 내내 `new-intent`로 판정하며 사다리를 매번 초기화했다.

원인을 신호별로 분해하면:

| 발화 | `looks_rejected` | `_RETRY_MARK` | 앵커 대비 유사도 |
|---|---|---|---|
| 턴2 "아니 이렇게 복잡한 거 **말고**..." | **False** | False | 0.00 |
| 턴4 "저장이 안 되는 것 같은데?" | False | False | 0.00 |
| 턴5 "이제 저장은 되는데 클릭해도 안 열려" | False | False | 0.20 |
| 턴6 "처음부터 심플하게 **다시** 만들어줘" | **False** | True | 0.50 |

두 가지 실패가 겹쳤다.

1. **`looks_rejected`가 실제 반려어를 못 잡는다.**
   `_REJECT_PAT`은 `(이거|그거|이건|그건|이렇게|그렇게)\s*말고`를 요구한다.
   실제 발화는 `"복잡한 거 말고"` — **`거 말고`**다. 명사구가 앞에 오는
   가장 흔한 형태가 패턴에 없다. 턴6 `"처음부터 다시 만들어줘"`도
   패턴은 `처음부터\s*다시`인데 실제로는 `처음부터 심플하게 다시`로
   **부사가 끼어들어** 매칭 실패했다.

2. **버그 리포트는 어휘가 매번 다르다.**
   턴4·5는 같은 작업(메모장)의 연속 실패인데 공유 내용어가
   `저장`·`되는` 정도라 `shared>=2` 문턱을 못 넘는다.
   사람은 "안 되는 증상"을 말하지 "아까 그거"라고 안 한다.

> **결론: 사다리 B의 트리거는 실로그에서 작동하지 않는다.**
> 문서에 적힌 "짧은 재요청 58%→100%"는 개발자가 만든 예문 기준이고,
> 실제 세션 로그에서는 **0%**다. 이건 세션 메모리에 "가정값"으로
> 표시해 둔 항목이 아니라, **실측으로 반증된 항목**이다.

## 3. 대조군 — 페르소나 B는 왜 사다리가 필요 없었나

같은 사람, 같은 목표, 같은 결과물(`memo.html`). 2턴에 끝났다.

| | A (원칙 0개) | B (원칙 전부) |
|---|---:|---:|
| 턴 수 | 6 | 2 |
| 반려 턴 | 5 | 0 |
| 입력 토큰 | 79,130 | 2,838 |
| 출력 토큰 | 29,853 | 1,746 |
| 사고 토큰 | 19,440 | 1,015 |
| **비용** | **$1.0361** | **$0.0498** |

**20.8배.** A의 리워크 5턴이 만든 초과비용은 **$0.9863**이다.

B의 턴2는 `"640px에서 목록 폭 110px이 너무 좁다. 140px로."` —
**수치를 지정한 지시**지 반려가 아니다. 분류기도 `unknown`을 냈지만
이건 정답이다. 반려가 아니니 분류할 것이 없다.

B가 리워크를 안 겪은 이유는 모델이 좋아서가 아니라
**스펙에 완료조건(`새로고침 후 데이터 유지`·`목록 클릭 시 정상 로드`)을
미리 박아뒀기 때문**이다. A가 턴4·5에서 태운 $0.986이 바로
그 두 줄을 안 써서 낸 비용이다.
