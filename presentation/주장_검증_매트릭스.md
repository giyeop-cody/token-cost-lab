# 주장 → 검증 → 반영 매트릭스

이 발표의 모든 문장은 두 관문을 통과했다.

1. **원안 검증** — 사용자가 제시한 주장을 그대로 싣지 않고, 원자료 재집계 또는 논문·공식 문서로 확인
2. **자체 검증** — 만든 슬라이드의 숫자가 원자료와 일치하는지 회귀 테스트(`verify_deck.py` 96건)

판정 기호: **○ 참** · **△ 조건부 참(문안 정밀화)** · **✗ 거짓(폐기 또는 재작성)**

---

## 1. 원안 5개 주장 — 1차 발표 (본편·보너스)

| # | 원안 주장 | 판정 | 실측 근거 | 슬라이드 반영 |
|---|---|---|---|---|
| 1 | 한국어가 영어보다 토큰을 많이 먹는다 | **○** | tiktoken o200k 6문장 실측 **1.44×** (cl100k는 2.22×) | 원칙 ① |
| 2 | 추론(사고)은 영어로 시키는 게 유리하다 | **○** | N=80 벤치, $/1,000자 reason **1.36×** CI[1.23, 1.51] p=6.08e−10 | 원칙 ① |
| 3 | 출력 토큰이 입력보다 2~8배 비싸다 | **○ (+보강)** | 벤더 단가표 2~8× 확인. **여기에 사고 토큰을 더하면 240×** (스윕 실측) | 슬라이드 2 · 24 |
| 4 | 장황한 설명이 비용을 키운다 | **○** | 장황 342tok → 간결 58tok = **−83%** | 원칙 ③ |
| 5 | 웹에서 추론시키고 결론만 주입하면 싸진다 | **○** | vibe $1.75 → 규약 $1.09 → SDD $0.51 = **−71%** | 원칙 ④ |

### 원안을 그대로 싣지 않은 것 — 반증 1건

| 주장 | 판정 | 왜 | 조치 |
|---|---|---|---|
| SDD(스펙 주도 개발)는 항상 싸다 | **△** | 자체 실측은 −71%인데, **Spec-Kit 방식은 오히려 +97~109%** 증가 | "SDD는 조건부로만 참" 슬라이드를 **따로 만들어** 자기 반증을 실었다 (보너스 5) |

## 2. 원안 주장 — 후속 발표 (에이전트 셋팅)

사용자가 제시한 셋팅 7개 항목 중 **검증이 필요한 2개**를 지정 요청했고, 둘 다 원안대로 싣지 않았다.

### 2-1. "코딩은 이미 결정된 사항에서는 성능차가 없음" → **✗ → 정밀화**

> **원안(✗):** "코딩은 이미 결정된 사항에서는 성능차가 없다"
> **정밀화(○):** "세 조건이 **동시에** 만족될 때 격차가 좁혀지거나 역전된다"

| 조건 | 근거 | 출처 |
|---|---|---|
| ① 스펙이 확정됐을 때 | 요구사항 분류에서 8B vs 상위 모델 **F1 격차 평균 0.02** | arXiv 2510.21443 |
| ② 출력 검증 수단이 있을 때 | 단위 테스트로 후보 선별 시, **고정 컴퓨트 예산에서 7~13B가 34~70B를 최대 15% 상회** | arXiv 2404.00725 |
| ③ 임계 크기 이상일 때 | 3B 미만은 유의하게 하락(Tukey HSD). 단 Qwen2.5-Coder 1.5B가 CodeLlama 7B를 이기는 반례 존재 | arXiv 2507.03160 |

**반대 근거도 같은 슬라이드에 실었다** (체리피킹 방지):
- pass@1을 10% 올리려면 **VRAM 약 4배** 필요 — 공짜가 아니다
- Rosetta Code 번역에서는 파라미터 수에 따라 성능이 **계속 스케일**한다 (Neurocomputing S0925231225021332)
- **스펙이 모호하거나 다단계 추론이 필요하면 격차는 그대로 남는다**

→ 슬라이드 7 「"결정된 사항은 성능차가 없다" — 절반만 맞다」

### 2-2. "배치는 24시간이라지만 보통 10분 이내 시작" → **✗ → 정밀화**

> **원안(✗):** "보통 10분 이내 시작" — **공식 근거 없음**
> **정밀화(○):** "SLO는 24시간이고, 부하에 따라 실제로 소진되며 `expired` 실패가 발생한다"

| 벤더 | 할인 | 공식 문구 | 실제 |
|---|---|---|---|
| OpenAI Batch | −50% | 24시간 내 완료 | 미완 시 **`expired`** 상태로 실패 |
| Google Gemini | −50% | **SLO** 24시간 | 대형 잡은 분할 권장 |
| xAI | −50% | 대부분 24시간 내 | **best effort · 보장 없음** |
| Anthropic | −50% | 24시간 내 | 대부분 1시간 내 종료 |

**결정적 반례:** 2025년 2월 OpenAI 커뮤니티 — 기존 1~2시간에 끝나던 잡이 **24시간에 근접**, expire 비율이 **0% → 25% 이상**으로 악화. 대응은 배치 크기 축소·모델 버전 고정이었다.

→ 그래서 배치는 세 조건을 모두 만족할 때만 쓴다: ① 턴 간 의존 없음 ② 마감 없음 ③ **expire 재시도 경로 설계**(`fallback: sync-after-2h`)

→ 슬라이드 8 「배치 — 단가는 반값, 시간은 약속이 아니다」

### 2-3. Playwright 웹 세션 자동 조작 → **방법은 싣되 리스크 병기**

기술적으로 동작하지만 **각 서비스 약관의 자동화 금지 조항**에 저촉될 수 있다. 같은 슬라이드에 대안 4행을 병기했다.

| 경로 | 종량 비용 | 권장도 |
|---|---|---|
| 사람이 직접 붙여넣기 | 0원 | **권장** |
| API + reasoning_effort 조정 | 종량 | **권장** |
| Batch API | −50% | 조건부 |
| Playwright 자동 조작 | 0원 | **비권장** (약관 리스크) |

→ 슬라이드 6 「추론은 정액제 창구로 — 그리고 그 대가」

## 3. 자체 검증 — 내가 만든 슬라이드도 의심했다

원안이 맞아도 **슬라이드가 원자료와 다른 말을 하면** 발표장에서 무너진다. 원자료 110행을 독립 재집계해 20건을 잡았다.

### 치명 3건 (반박당하면 신뢰 붕괴)

| # | 문제 | 실제 | 조치 |
|---|---|---|---|
| 1 | "답변은 여섯 번 다 같은 숫자" | 문자열이 같은 건 **1개 조건뿐**. 사고를 끈 조건에서 `380.16` 자릿수 오류 1회 발생 | 표의 마지막 열을 **정답률(n/6)**로 교체. 논지가 오히려 강해짐 — "정답률은 같은데 요금만 240배" |
| 2 | "512는 오답을 냈다" (6회 중 1개만 표시) | 실제로는 **6회 중 4회 오답** = 정답률 33% 붕괴 | "정답 2/6 ← 품질 붕괴"로 교체. 원래 주장보다 강한 근거를 약하게 쓰고 있었다 |
| 3 | "1,000 토큰이 0.3센트 / 15센트" | Sonnet 단가로는 0.03 / 1.5센트. **절대값이 전부 10배 틀림** | "10,000 토큰"으로 수정 |

### 중대 4건

| # | 문제 | 조치 |
|---|---|---|
| 1 | 표에 행 하나 누락 — 5행 합이 합계와 불일치 | 누락 행(에러 분석문) 복원 |
| 2 | 슬라이드 16과 17의 **기준선이 다름** (62% vs 68%) | $8.55로 통일. $10.05는 "켰는데 매번 미스 **+18%**" 경고 행으로 분리 → **캐싱을 잘못 켜면 안 켠 것보다 비싸다**는 교훈이 추가로 나옴 |
| 3 | 240배가 **단가 가정에 의존** (실제 호출 모델 단가로는 149배) | 각주에 단가 전제 명시 + 도구가 민감도를 자동 출력 |
| 4 | "Latin 59.5%" — 어떤 기준으로도 재현 불가 | o200k 20만 어휘 직접 스캔 → **67.2%**로 교체 (한글 1.2%는 정확했음) |

### 검증 통과 항목 (재계산해서 소수점까지 일치)

- N=80 벤치 전체 · 통계 검정(부트스트랩 CI · Welch · Cliff's δ) · 사고 예산 스윕 비용 240.0×
- exp01 토크나이저 · exp03 캐싱 62%/손익분기 0.28회 · exp02·04·05·06·09 전량 재실행
- **조작이나 체리피킹의 흔적은 없었다.** 문제는 전부 "데이터가 말하지 않은 것을 슬라이드가 말한 부분"에 몰려 있었다.

## 4. 검증을 자동화했다 — 사람이 매번 대조할 수 없으니까

### `tools/verify_deck.py` — 96개 검사, 실패 시 exit 1

| 검사 범주 | 잡는 오류 |
|---|---|
| 원자료 재계산 vs 슬라이드 표기 | 수치 불일치 |
| **정답률 재집계** | "답이 다 같다" 류의 과장 |
| 표 행 합계 = 표기 합계 | 행 누락 |
| 슬라이드 간 기준선 일관성 | 같은 지표 다른 값 |
| 단위 검사 | 자릿수 오류 |
| 덱 텍스트 금칙어 | 수정 전 문구 잔존 |

**검사기 자체도 검증했다.** 고친 오류를 일부러 되살려 양방향으로 검출됨을 확인했다 — 통과만 하는 테스트는 테스트가 아니다.

> 설계 원칙: 검사기는 실험 코드를 **재구현하지 않고 임포트**한다. 처음엔 직접 계산했다가 $2.44 vs $2.32로 어긋났는데, **덱이 아니라 검사기가 틀렸다.** 검사기가 자기 계산식을 들면 그게 또 하나의 진실 공급원이 된다.

### `agent_setup/test_router.py` — 32/32 PASS

후속 덱의 라우터는 슬라이드용 의사코드가 아니라 **실제로 도는 코드**다. 표준 라이브러리만 쓰므로 네트워크 없이 라이브 시연이 된다.

초기 버그도 슬라이드에 그대로 남겼다 — "src 밑 TODO 전부 grep"이 BULK로 오분류돼서, TOOL 규칙을 BULK 앞으로 옮겨 해결했다. **규칙 기반 라우터의 버그는 대부분 순서 버그이고, 테스트가 그걸 잡는다.**

### `check_layout.py` + PDF 육안 검수

텍스트 검사만으로는 못 잡는 게 있다. LibreOffice가 Consolas를 NanumGothicCoding으로 치환하면서 글자 폭이 커져, 검사기는 통과했는데 실제 PDF에서 코드 블록이 박스를 넘었다. **45쪽 전부를 이미지로 렌더링해 눈으로 확인**했고 4건을 추가로 고쳤다.

## 5. 발표장에서 반박당하지 않으려면

|---|---|---|
| 슬라이드 25 | "**정답률**은 6/6으로 같은데 요금만 240배" | ~~"답이 여섯 번 다 같았다"~~ |
| 240배 언급 시 | "**이 단가 기준으로** 240배" | ~~"무조건 240배"~~ |
| "512가 왜 나쁘냐" 질문 | "6회 중 4회 오답. 단 **n=6이라 CI가 겹쳐서 경향으로만** 본다" | ~~"512는 확실히 나쁘다"~~ |
| 코딩 성능차 질문 | "**세 조건이 만족될 때** 좁혀진다. VRAM 4배 반대 근거도 있다" | ~~"작은 모델도 똑같다"~~ |
| 배치 시간 질문 | "**SLO는 24시간**. 빠른 경우가 흔할 뿐 약속은 아니다" | ~~"보통 10분이면 시작된다"~~ |
