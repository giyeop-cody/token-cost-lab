# 원안 2건을 왜 다시 썼나 — 상세 근거

발표 중 "그 근거가 뭐냐"는 질문이 들어올 지점입니다. 슬라이드에 다 못 넣은 배경을 여기 둡니다.

---

# 1. "코딩은 이미 결정된 사항에서는 성능차가 없음"

## 1-1. 왜 이 문장을 그대로 실을 수 없었나

주장의 방향은 맞습니다. 문제는 **"없다"는 단어**입니다.

"성능차가 없다"는 **전칭 명제**입니다. 반례 하나면 무너집니다. 그리고 반례는 쉽게 나옵니다 — 청중 중 누군가 "우리는 작은 모델로 바꿨다가 실패했다"고 하면 그 자리에서 끝납니다. 실제로 그런 실패는 흔합니다.

더 중요한 건, **이 문장대로 실행하면 손해를 본다**는 점입니다. "결정만 됐으면 아무 모델이나 된다"고 믿고 1B 모델에 붙이면 실패합니다. 정확히 어떤 조건에서 성립하는지를 모르면 적용할 수가 없습니다.

그래서 **"없다"를 "어떤 조건에서 좁혀지는가"로 바꿨습니다.** 방어 가능하면서 실행 가능한 문장으로요.

## 1-2. 근거 — 조건 3개

### 조건 ① 스펙이 확정됐을 때

**arXiv 2510.21443 — Does Model Size Matter?**

요구사항 분류 과제에서 SLM과 LLM을 비교했습니다.

| 모델 | F1 (3개 데이터셋) |
|---|---|
| Llama-3-8B | 0.76 / 0.78 / 0.88 |
| 대형 LLM | 0.81 / 0.80 / 0.89 |
| **평균 격차** | **0.02** |

**판단이 이미 끝난 작업**은 모델 크기를 덜 탑니다. 분류·판정처럼 "무엇을 할지"가 정해진 일에서는 8B가 대형과 거의 같습니다.

이게 원안 주장의 **가장 강한 지지 근거**입니다. 실제로 격차가 0.02면 실무에서 무시 가능합니다.

### 조건 ② 출력 검증 수단이 있을 때

**arXiv 2404.00725 — The Larger the Better? Improved LLM Code-Generation via Budget Reallocation**

이게 제일 흥미로운 논문입니다. 질문이 이겁니다: *같은 컴퓨트 예산이라면, 큰 모델 한 번 vs 작은 모델 여러 번 중 뭐가 낫나?*

- **고정 컴퓨트 예산에서 7B/13B가 34B/70B를 최대 15% 상회** (HumanEval·MBPP)
- Code Llama 7B/13B는 60% 도달에 **대형 모델의 1/4 시간**

단 **전제가 있습니다.** 단위 테스트로 후보를 걸러낼 수 있어야 합니다. 작은 모델을 여러 번 돌려서 그중 맞는 걸 고르는 방식이니까요.

**검증 수단이 없으면 이 논리는 통째로 무너집니다.** 여러 개 뽑아놓고 뭐가 맞는지 모르면 의미가 없습니다. 그래서 이걸 조건으로 걸었습니다.

→ 후속 덱의 라우터가 `implement`에 **`explain: 3-lines`와 테스트 강제**를 붙이는 이유가 여기 있습니다. 검증 수단이 있어야 중간 모델로 내려도 안전합니다.

### 조건 ③ 임계 크기 이상일 때

**arXiv 2507.03160 — Assessing Small Language Models for Code Generation**

0.4B~10B 20개 모델 × 5개 벤치마크(HumanEval, MBPP, Mercury, HumanEvalPack, CodeXGLUE).

- **모델 크기는 성능에 통계적으로 유의미한 영향** (Tukey HSD: 3B~10B 그룹이 그 아래 그룹을 pass@1에서 유의하게 상회)
- 단 **pass@2/5/10에서는 유의성이 경계선**으로 약해짐 — 여러 번 시도할 수 있으면 격차가 줄어든다는 뜻으로, 조건 ②와 맞물립니다
- **pass@1을 10% 올리려면 VRAM 약 4배**

**중요한 반례:** OpenCodeInterpreter 1.3B(pass@1 0.53), Qwen2.5-Coder 1.5B(0.54)가 **CodeLlama 7B·StarCoder2 7B보다 우수**했습니다. 상위군은 0.59~0.67.

→ 즉 **크기 자체보다 학습·설계 품질**입니다. 다만 일정 임계 아래로는 확실히 떨어지고, 임계 위에서는 수확 체감이 옵니다. 그 임계를 대략 **3B~7B**로 잡았습니다.

## 1-3. 반대 근거도 같이 실은 이유

**Neurocomputing S0925231225021332 — Performance and interpretability analysis of code generation LLMs**

Rosetta Code 번역 과제에서는 **CCR과 pass@1이 파라미터 수에 따라 계속 스케일**합니다. 위 논문들과 반대 방향입니다.

이걸 왜 슬라이드에 넣었냐면 — **넣지 않으면 체리피킹이기 때문입니다.** 유리한 논문 3편만 고르면 반대 논문 한 편에 무너집니다. 먼저 말하면 그게 방어가 됩니다.

그리고 이 논문은 조건을 정밀화하는 데 실제로 도움이 됩니다. Rosetta Code 번역은 **다단계 추론이 필요하고 스펙이 느슨한** 작업입니다. 즉 조건 ①이 깨진 경우입니다. 반례가 아니라 **경계선을 보여주는 사례**입니다.

## 1-4. 최종 문안

> **원안(✗):** "코딩은 이미 결정된 사항에서는 성능차가 없다"
>
> **정밀화(○):** "① 스펙이 확정되고 ② 출력 검증 수단이 있고 ③ 작업이 임계 크기(≈3B~7B) 이상 모델의 능력 범위 안에 있을 때, 격차가 좁혀지거나 역전된다. 반대로 스펙이 모호하거나 다단계 추론이 필요하면 격차는 유지된다."

**실행 지침으로 번역하면:** 스펙이 확정된 구현은 MID로 내리되, 반드시 테스트를 붙인다. 테스트가 없으면 내리지 않는다.

## 1-5. 예상 질문 대비

| 질문 | 답변 |
|---|---|
| "그래서 몇 B를 쓰라는 거냐" | "임계는 대략 3B~7B인데, **크기보다 학습 품질**입니다. Qwen2.5-Coder 1.5B가 CodeLlama 7B를 이깁니다. 후보를 정해서 여러분 작업으로 직접 재보셔야 합니다." |
| "우리는 작은 모델로 바꿨다가 실패했다" | "세 조건 중 뭐가 빠졌는지 보시면 됩니다. 대개 **②검증 수단**입니다. 테스트 없이 내리면 실패합니다." |
| "15% 역전이 진짜냐" | "**고정 컴퓨트 예산**이라는 전제가 붙습니다. 작은 모델을 여러 번 돌려 테스트로 거르는 방식입니다. 무조건 이긴다는 뜻이 아닙니다." |

# 2. "배치는 24시간이라지만 보통 10분 이내 시작"

## 2-1. 왜 이 문장을 그대로 실을 수 없었나

**"보통 10분 이내"라는 수치의 출처를 찾을 수 없었습니다.** 어느 벤더도 이런 약속을 하지 않습니다.

경험적으로는 맞을 수 있습니다. 실제로 작은 잡은 빨리 끝납니다. 문제는 이게 **개인 경험을 일반 규칙처럼 말하는 형태**라는 점입니다.

그리고 이 문장대로 설계하면 **장애가 납니다.** "10분이면 되니까 배치에 넣자"고 파이프라인을 짜면, 부하가 걸린 날 24시간을 기다리거나 `expired`로 실패합니다. 폴백이 없으면 그대로 멈춥니다.

## 2-2. 벤더 공식 문구 — 아무도 시작 시각을 약속하지 않는다

| 벤더 | 할인 | 공식 문구 | 함의 |
|---|---|---|---|
| **OpenAI Batch** | −50% | "각 배치는 **24시간 내 완료**(often more quickly)" | 미완 시 **`expired`** 상태. `completion_window`는 현재 **24h 단일 옵션** |
| **Google Gemini** | −50% | **SLO 24시간**, "다수는 훨씬 빠름" | 대형 잡은 분할 권장 |
| **xAI** | −50% | "대부분 24시간 내" | **best effort이며 보장 없음** |
| **Anthropic** | −50% | 24시간 내 | 대부분 1시간 내 종료 |

전부 **완료 상한**을 말합니다. **시작 시각을 말하는 벤더는 없습니다.** "often more quickly"는 마케팅 문구지 SLA가 아닙니다.

OpenAI 상태값은 `validating → in_progress → finalizing → completed`이고, 미완 시 **`expired`**입니다. 즉 **실패 상태가 API에 정식으로 정의되어 있습니다.** 벤더가 실패를 예상하고 있다는 뜻입니다.

## 2-3. 결정적 반례 — 실제로 24시간을 쓴 사례

**OpenAI 커뮤니티, "The GPT-4o Batch API has been extremely slow" (2025-02)**

- 기존 **1~2시간**에 끝나던 잡이 **24시간에 근접**
- **expire 비율이 0% → 25% 이상**으로 악화
- 다수 사용자가 동일 보고
- 대응: 배치 크기를 절반으로 축소, 모델 버전 고정(gpt-4o-2024-11-20)으로 회피

이게 핵심입니다. **"보통 빠르다"가 참이어도, 느려지는 날이 실재하고 그날 25%가 실패했습니다.**

**Inspect AI 배치 가이드** (inspect.aisi.org.uk/models-batch.html)도 같은 이야기를 합니다: "일반적으로 1시간 내이나 최대 24시간." 그리고 결정적인 지적을 합니다 —

> **에이전트형(다단계·가변 생성) 워크로드는 배치에 부적합하다.** 매 턴마다 배치 대기가 누적되어 수시간~수일이 된다.

이건 저희 후속 발표 주제와 직결됩니다. **에이전트 루프 안에 배치를 넣으면 안 됩니다.** 턴마다 대기가 곱해집니다.

## 2-4. 긍정 사례도 확인했다

반대쪽도 봤습니다. 원안이 완전히 틀린 건 아닙니다.

- **ZenML 블로그** — 5건 제출 시 **11초** 회수
- **daniel-gomm.com** — 순차 처리 10시간 분량이 단일 배치 **1시간 미만** 완료

**소규모 잡은 실제로 수초~수분에 끝납니다.** 원안의 체감은 정확했습니다. 다만 그건 **보장이 아니라 관측**입니다. 그 차이를 문장에 담아야 합니다.

## 2-5. 최종 문안

> **원안(✗):** "24시간이라지만 보통 10분 이내 시작"
>
> **정밀화(○):** "SLO는 24시간이다. 소규모 잡은 수초~수분에 끝나는 경우가 흔하지만, 시스템 부하에 따라 24시간을 소진하고 `expired`로 실패하는 일이 실제로 발생한다."

**실행 지침 3조건:**

| 조건 | 이유 |
|---|---|
| ① **턴 간 의존이 없을 것** | 에이전트형 다단계 작업은 대기가 누적된다 |
| ② **마감이 없을 것** | 사람이 기다리는 작업에 24시간을 걸 수 없다 |
| ③ **expire 재시도 경로를 설계할 것** | `fallback: sync-after-2h` — N시간 내 미완이면 동기 처리로 전환 |

→ 라우터 코드의 `bulk` 분기가 정확히 이걸 구현합니다:
```python
{"window": "24h", "fallback": "sync-after-2h"}
```
그리고 `deadline_sensitive=True`면 배치로 보내지 않고 MID 동기 처리로 돌립니다.

## 2-6. 예상 질문 대비

| 질문 | 답변 |
|---|---|
| "우리는 항상 10분 안에 됐는데" | "저도 그렇습니다. 그게 **관측이지 보장이 아니라는 게** 요점입니다. 2025년 2월에 expire 25%가 실제로 났습니다." |
| "그럼 배치를 쓰지 말라는 거냐" | "아닙니다. **−50%는 큰 절감**입니다. 세 조건만 확인하고 쓰라는 겁니다. 특히 폴백은 필수입니다." |
| "폴백을 어떻게 짜냐" | "제출 시각을 기록하고, N시간 지나면 동기 API로 재제출합니다. 라우터에 `sync-after-2h`로 들어 있습니다." |
| "에이전트에 배치를 넣으면?" | "**넣지 마세요.** 턴마다 대기가 곱해집니다. Inspect AI 가이드가 명시적으로 경고합니다." |

# 3. 두 건에 공통으로 적용한 원칙

두 문장 모두 **틀린 게 아니라 조건이 빠져 있었습니다.**

| 원안 | 실제 상태 | 빠진 것 |
|---|---|---|
| "성능차가 없다" | 특정 조건에서는 참 | **조건 3개** |
| "보통 10분 이내" | 소규모 잡에서는 흔한 관측 | **보장이 아니라는 단서 + 실패 경로** |

그래서 처리 방식도 같았습니다.

1. **전칭을 조건부로 바꾼다** — "없다" → "이럴 때 좁혀진다"
2. **반대 근거를 같은 화면에 싣는다** — 체리피킹 방지, 선제 방어
3. **실행 지침으로 번역한다** — 조건을 코드에 넣는다(테스트 강제, 폴백 경로)

이게 SDD와 DRY를 다뤘던 방식과 동일합니다. 1차 발표에서 SDD가 조건부로만 참이라는 걸 자기 반증으로 실었던 것과 같은 처리입니다.

**발표에서 이렇게 말하면 됩니다:** "제가 원래 이렇게 알고 있었는데, 찾아보니 조건이 붙더라. 그 조건을 코드에 넣었다." 이게 가장 강한 형태입니다.
