# 토큰 라우팅 규칙

이 워크스페이스에서 작업할 때는 `token-router` MCP 서버의 판단을 따른다.

사다리 축소(Lean) 적용 후 기본값은 **3칸** 사다리다
(`widen → reset → respec`). 7칸 원본이 필요하면 `rework_next`에
`ladder="full"`을 넘긴다. 라이브 시연과 덱(이미 3칸)을 정렬하기 위해
기본은 3칸으로 맞췄다.

## 1. 작업 시작 전 — 반드시 `route_task`

새 요청을 받으면 코드를 쓰기 전에 `route_task`를 먼저 부른다.
반환된 `tier`와 `options`를 그대로 따른다.

- `max_out_tok`이 있으면 그 안에서 끝낸다.
- `explain: 3-lines`면 설명은 3줄. 요청받지 않은 해설을 붙이지 않는다.
- `tier: web`이면 정액제 웹 세션으로 보낸다(토큰 과금 없음).
- `prefer: code-execution`이면 모델에게 시키지 말고 코드로 처리한다.

## 2. 실패/반려가 왔을 때 — `rework_next` (같은 방식 재시도 금지)

검증이 실패하거나 사용자가 "다시"라면, 같은 프롬프트를 다시 던지지 않는다.
`rework_next`를 부르고 받은 칸만 올린다. **한 번에 축 하나씩**이다.

사다리는 두 축이 다르게 돈다.

- **A축(내부 검증 실패)** — 테스트/AC가 트리거. 에이전트가 모르는
  사이 올라간다. 사용자는 개입하지 않는다.
  | 회차 | 칸 | 무엇이 바뀌나 |
  |---|---|---|
  | 2 | `retry` | 그대로. 증거(실패 테스트·diff)만 추가 |
  | 3 | `widen` | 범위만 확대. 모델은 그대로 |
  | 4 | `tier-up` | 모델 상승. 단 **진단 400토큰만**, 적용은 아래 티어 |
  | 5 | `respec` | 구현 중단. 스펙 다시 쓰고 사람에게 |

- **B축(사용자 의도 반복)** — 사용자가 같은 의도를 다시 말하는 것이
  트리거. 결과물이 이미 한 번 나갔으므로 그 턴 출력은 전액 지불된 상태다.
  기본 3칸 순서:
  | 차수 | 칸 | 무엇이 바뀌나 |
  |---|---|---|
  | 1 | `widen` | 범위 확대. 모델은 그대로 |
  | 2 | `reset` | 세션 갈기. **입력 누적이 여기서 끊긴다** |
  | 3 | `respec` | 구현 중단. 스펙 다시 잡는다 |

**조건부 tier-up — 모델을 올리는 건 다섯 중 하나뿐.** 의도불일치 5종
(범위·취향·전제·판단오류·맥락오염) 중 티어 상승이 정답인 건
`reasoning`(판단 오류) 하나뿐이다. 그래서 `rework_next`는 기본 사다리에
`tier-up` 상시 칸을 두지 않는다. 분류가 `reasoning`으로 판정된 경우에만
모델을 올린다 — `rework_next`에 `mismatch="reasoning"`을 넘기거나,
사용자 발화 자체를 `classify_mismatch`로 판정하게 둔다. 취향·범위 불일치에
LARGE를 붙이는 건 돈만 쓰고 안 고쳐진다.

**리워크 턴에서 파일 전문을 다시 쓰지 않는다.** 진단 몇 줄 + 통합 diff만
낸다. 이 비용의 81~92%가 출력 토큰이라 여기가 가장 큰 절감 지점이다.

## 3. 매 턴 끝 — `session_check`

- `continue` 그대로 진행
- `compact` 스레드는 유지하고 결론만 남긴다
- `reset` 새 세션. `carry_over`에 적힌 것만 들고 간다

**반복만으로는 리셋하지 않는다.** 리셋은 완료된 결과가 원하던 방향이
아닐 때만 나온다. 맥락을 부수는 비용이 크기 때문이다.

## 4. 설명 — `trim_explain`

"자세히 / 깊게 / 문서로"를 명시적으로 요청받지 않은 모든 설명은
`trim_explain`을 통과시킨다.

## 5. 리워크 비용의 지배항은 입력 누적이다

사다리가 싼 이유는 **좋은 모델을 쓰는 게 아니다.** 제자리에서 다시
시키면 대화 전체가 다음 턴 입력에 통째로 다시 실려, 턴당约 4,700토큰씩
불어난다. 사다리의 이득은 `reset` 칸에서 이 누적을 끊는 데서 난다.

- `turn_growth_tok` ≈ 4,700은 페르소나 시나리오의 총 입력 증가분에 맞춘 값이다. 독립 실측 캘리브레이션이 아니며, 이전 출력이 이미 포함되어 있으므로 출력을 다시 더하지 않는다. `analysis/calibrate_growth.py`의 동일 자료 내부 정합만 확인했다.
- 입력을 빼고 계산하면 실제 비용의 절반만 본다 — 누적을 항상 넣어 비교한다.
- 짧은 리워크에서도 사다리는 이득이다: 1턴 26%, 2턴 45% 절감.

## 금지 — 이 문장들은 쓰지 않는다

- "사다리가 12배 절감" — 대조군을 최상위 모델로 잡았을 때만 나오는 수치.
- "스펙 선주입이 사다리를 이긴다" — 반려 0턴 세션 vs 5턴 세션, 축이 다르다.
- "tier-up은 쓸모없다" — reasoning 계열에서는 필요하다. 상시가 아니라
  **조건부**일 뿐.
